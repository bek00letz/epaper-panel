# Audit, 19 October 2026

A second, sceptical look at the E-paper panel add-on and its firmware, after
the 0.9.x rebuild. Audited: `main` at `9a5d6b4` (version 0.10.0, which is what
Home Assistant is running today), not 0.9.7 as first briefed.

**How it was checked.** Read the add-on, the firmware core and client, and the
YAML template; ran the suite (117 tests pass); wrote throwaway harnesses for
every finding below (kept outside the repository); fuzzed the firmware's frame
parser on this Mac with AddressSanitizer and UndefinedBehaviorSanitizer; and
read the live add-on's log and entity states through Home Assistant's
read-only tools. Nothing was changed in Home Assistant or on the panel.

**Not re-reported** (already known): Flightradar24 being unofficial, frames
served without the token until the panel first uses it, the editor UI items
the redesign session owns, and battery deep sleep.

**Ranking.** Most severe first. "Likelihood" is for this home: the panel
fetches every minute, quiet hours are off, and the add-on runs a Jellyfin
source, three statistics sources, a flight widget, and remote access through
Cloudflared.

## 1. The add-on writes its Home Assistant token, and other secrets, into its log — High

**What.** When a call to Home Assistant or a data source fails, the error is
printed with `repr(exc)`. aiohttp's `ClientResponseError` includes the request
headers when printed, so the line contains `Authorization: Bearer <the
add-on's Supervisor token>`, Jellyfin's `X-Emby-Token`, or a REST source's
secret headers.

**Where.**
- `addon/app/sources/ha_services.py:78`, `:130` (weather, calendar), `addon/app/ha.py:83` (actions), `addon/app/feeds/__init__.py:102` (every data source)
- Any `ha_json` failure reaching `server.py:79-80` (`render loop error`), which also stores the text in `FRAMES.error`, served by `/api/status`
- `addon/app/web.py:402`: `/api/entities` sends `repr(exc)` to the browser

**Seen live.** Today's add-on log has a `fetch_weather_forecast error for
weather.forecast_home: ClientResponseError(...)` line, from the 502 errors
while Home Assistant restarted at 15:15. It contains the full bearer token. I
haven't copied it anywhere.

**Repro.** Point `HA_BASE` at a server that answers 502 and call
`ha.ha_json(...)`. The printed error contains the token. The same goes for a
Jellyfin source whose server returns an error: the line contains the API key
(harness `h4_token_log.py`).

**What happens.** Anyone who can read the add-on's log can call Home
Assistant's API as the add-on: Supervisor logs in the UI, a downloaded log
attached to a GitHub issue, a log-shipping add-on, or an AI tool with log
access. The same applies to the Jellyfin key.

**Likelihood.** Certain. It already happened, and it happens on every Home
Assistant restart and every source outage.

**Fix.**
- Add one helper, `describe(exc)`, that returns the type, the HTTP status and the URL path, never the headers. Use it in all 30-odd `{exc!r}` prints and both API responses.
- Add a test that fails if a fake token shows up in captured output.
- Treat the token as exposed. I couldn't confirm whether the Supervisor issues a new add-on token on restart. Don't share today's logs until it has changed.

## 2. Data sources run inside every render, so a slow source holds up the panel and every Send, and a statistics source can hang it — Medium

**What.** `build_frames` starts with `publish_computed`, which awaits every
configured source one after another (`feeds.run_all`). The Jellyfin and REST
fetches have 15 s timeouts. The statistics source's websocket reads have no
timeout at all. This contradicts the rule "a render never waits on an outside
service": only `sources/` go through `live_data`, and `feeds/` don't.

**Where.** `addon/app/frames.py:305`, `addon/app/entities.py:110-116`,
`addon/app/feeds/statistics.py:17-28`. Compare `hass.py:62-70`, which does pass
timeouts.

**Repro** (`h2_feeds_block.py`):
- A REST source whose server takes 12 s to answer: `refresh_frames` took **12.1 s**.
- A websocket that accepts the connection and never speaks: `statistics.fetch` was **still waiting after 40 s**.

**What happens.**
- Every render waits for the slowest source.
- *Send to panel* (`PUT /api/layouts`), *Push*, the Refresh button and the action endpoint all wait too, so the editor appears stuck.
- If Home Assistant accepts the websocket and then stalls, all rendering stops until that connection dies.

**Likelihood.** Medium. This home has a Jellyfin source and three statistics
sources. A Jellyfin box that's off or asleep adds seconds to every render. A
stalled websocket is rarer.

**Fix.** Run sources through `live_data` (`@runtime.live`) with a per-source
interval. Build the statistics query on `Hass.ws`, which has receive timeouts.

## 3. A source that fails for an hour gets its Home Assistant entity deleted — Medium

**What.** `EntityPublisher.sync` withdraws any value not refreshed for an hour
by publishing an empty discovery config. Home Assistant then deletes the
entity. "Not refreshed" includes "its source has been failing", because
`run_all` publishes nothing for a failed source.

**Where.** `addon/app/mqtt_bridge.py:116-119` (`STALE_AFTER`), with
`feeds/__init__.py:98-102` and `entities.py:113-116`.

**Repro** (`h3_withdraw.py`, fake broker and clock). After two healthy hours
of `sensor.epaper_watch`, the source fails. At **60 minutes** the discovery
topic is cleared (`mqtt: withdrew sensor.epaper_watch`).

**What happens.** The entity disappears from Home Assistant, along with any
area, name or icon set on it. Automations and dashboards that use it break
until the source recovers, and it then comes back as a new entity. The panel
itself keeps showing the old value (`runtime.PUBLISHED` is never pruned).

**Likelihood.** Medium. It needs Jellyfin off overnight, or the internet down
for over an hour (the sports and racing windows). The same rule also gives the
opposite bug: `sensor.epaper_closest_aircraft` keeps its last callsign while
`sensor.epaper_flights_overhead` reads 0. See live states, and finding 7.

**Fix.** Withdraw only values that no page and no configured source refers to
any more (decide from the configuration, not from freshness). When a source
fails, mark its entity unavailable through a per-entity availability topic.

## 4. A Home Assistant restart blanks the panel's values, drops conditional pages and re-fires alerts — Medium

**What.** While Home Assistant is restarting, the Supervisor answers 502.
`resolve_templates` turns every failed template into `""`.

**Where.** `addon/app/ha.py:58-69`, `frames.py:236-261` (`when` pages),
`frames.py:279-299` (alerts).

**Repro** (`h5_ha_down.py`). Values go from `'21.5'` to `''`. A door alert
with a 60-minute hold is released while Home Assistant is down, and **fires
again** when it comes back.

**What happens.**
- Rendered values show as blank or `--`, and the panel downloads that within a minute.
- Every `when` page leaves the rotation, which also triggers a push.
- When Home Assistant returns, the pages come back (another push), and every still-true alert fires again. That means a new hold, a forced full refresh, and a push.

The live log shows this pattern at 15:15 today.

**Likelihood.** High frequency, mild harm: every Home Assistant update or
restart.

**Fix.**
- Let `resolve_templates` tell "Home Assistant unreachable" apart from "empty answer".
- When it's unreachable, keep the last good value per key and skip the alert and `when` evaluation for that render. A render whose inputs are all stale could also skip publishing.

## 5. Two renders at once: the older one can win and put the old pages back — Medium-low

**What.** `refresh_frames` has no lock. It is called by the render loop, Send
(`PUT /api/layouts`), Push, the Refresh button over MQTT, the action endpoint
and the panel refresh-interval change, and these can overlap. Each build reads
`layouts.json` near its start. Whichever finishes last replaces
`runtime.FRAMES`.

**Where.** `addon/app/frames.py:534-575`, callers in `web.py`, `server.py:39-46`.

**Repro** (`h1_race.py`, check_alerts delayed 0.5 s on the loop's build only).
The user sends a 1-page rotation. After the save's render the frames show
`['solar']`. Then the loop's older render finishes, and the frames are
`['solar', 'solar_month']` again, while `layouts.json` says `['solar']`.

**What happens.**
- The panel is pushed the new pages, then pushed the old ones ("pages changed" again), for up to a minute.
- The alert state (`runtime.ALERT`) and the linger state are also updated by both builds.

**Likelihood.** Low-medium: about the share of each minute the loop spends
between reading the layouts and swapping the frames. Finding 2 widens that
window to many seconds.

**Fix.** An `asyncio.Lock` around build-and-swap, plus a "render again"
flag, so a request that arrives mid-render triggers exactly one more render
afterwards instead of a parallel one.

## 6. While resting (asleep or in quiet hours), a failed download is never retried — Medium-low

**What.** The add-on counts a wake-up as delivered once Home Assistant
accepts `refresh_now`. If the panel's download then fails (a Wi-Fi blip, the
add-on restarting), the YAML schedules a retry with `retry_fetch_in`. But the
5-second timer only fetches when `!panel.resting()`, and the panel is still
resting, because only a successful download can tell it quiet hours are over.

**Where.** `addon/app/firmware/panel.yaml:372-375` and `:394-399`,
`components/epf/epf_core.h:664`, `:682`.

**Repro** (`scen.cpp (a)`). The panel goes to sleep for quiet hours. In the
morning one download fails, and in the next 8 simulated hours it fetches
**0 times** and stays asleep.

A related gap: if the add-on restarts across the end of quiet hours, its first
render has nothing to compare against, so `quiet_changed` is false and nothing
is pushed (`frames.py:539-550`).

**Likelihood.** Low today, because quiet hours are disabled in this home. High
once they are turned on: one bad morning a month is enough to notice.

**Fix.**
- Firmware: keep a `fetch_owed` flag that survives resting, and retry with backoff even while resting.
- Server: push on the first render after a start if quiet hours are off, or carry "wake at" in the frame file so the panel can wake itself.

## 7. Flights: an old aircraft list is served as fresh when both services fail — Low-medium

**What.** If Flightradar24 and OpenSky both fail, `fetch_overhead_aircraft`
returns the cached list whatever its age. `live_data` treats that as a
success.

**Where.** `addon/app/sources/flights.py:183-184`, `entities.py:89-105`.

**Repro** (`h6_flights_stale.py`). With a cache 3 hours old and the network
down, it returns `[ROT123 at 4.2 km]`.

**What happens.**
- During an internet outage, the flight page stays in the rotation showing planes that left hours ago.
- `sensor.epaper_flights_overhead` keeps reporting them, which also defeats the hour-based withdrawal.
- Separately, when the count drops to 0, `sensor.epaper_closest_aircraft` keeps its last callsign. Live right now: overhead `0`, closest `PGT76LZ` at 25.1 km.

**Fix.**
- Give the fallback cache a maximum age (a few minutes), then return `[]`.
- Publish the closest aircraft as `none` (or unavailable) when the list is empty.

## 8. Renaming a data source silently erases its saved API key — Low-medium

**What.** Stored secrets are restored by the source's *name*
(`unmask_secrets`). If the name changes, the masked `••••••••` finds no match
and becomes `""`.

**Where.** `addon/app/feeds/__init__.py:68-84`. The new editor lets you rename
a source (`web/app/sheets.js:378`).

**Repro.** Rename `jelly` to `tv` and save: the key is saved as `''`.
**Test** with the new name fails the same way ("Nothing came back").

**What happens.** The source stops working after a rename with no error
shown, and its old entity is withdrawn an hour later (finding 3).

**Fix.** Give each source a stable id that the editor round-trips, and unmask
by id. At the least, have the editor send the original name with each source.

## 9. Panel setup bakes the browser's address into the panel's firmware — Low-medium

**What.** The default frame-server host is the `X-Forwarded-Host` of the
browser request that first opens Panel setup. It's saved immediately.

**Where.** `addon/app/web.py:583-587`, `panel_setup.py:36-53`.

**Repro** (`h8_host.py`). Open Panel setup through `ha.example-tunnel.com`.
The saved `ha_host` is `ha.example-tunnel.com`, and the YAML holds
`frames_url: "http://ha.example-tunnel.com:8099/frames.epf?token=…"`.

**What happens.** With Cloudflared or Nabu Casa, the panel is told to fetch
from the public hostname. That either fails, or sends the frame token in plain
HTTP across the internet if port 8099 is reachable there.

**Likelihood.** Low now that setup is done. It applies to a fresh install
opened remotely, and this home does use Cloudflared.

**Fix.** Default to Home Assistant's own LAN address from the Supervisor
(`/network/info`, or the core `internal_url`). Ignore forwarded hosts.

## 10. A frame file over 1 MiB never loads, and nobody is told — Low

**What.** The panel's buffers are 1 MiB each (`epf_client.h:25`), so a
rotation with too many pages comes back as `ERROR_BUFFER_FULL`. The panel
keeps its old frames and re-downloads the full file every 30 s. The limit is
38 pages on the 5.79", 21 on the 7.5" and 13 on the 10.2". Repeated rotation
entries and sub-items (up to 5–6 each) count towards it.

There is also an off-by-one: a file of exactly 1 MiB is rejected
(`epf_client.h:149`).

**Where.** `components/epf/epf_client.h:25`, `:147-155`. Nothing in
`frames.build_frames` or `epf.encode_epf` checks the size.

**Likelihood.** Low here: about 12 pages, under 350 KB today. It's easy to
reach on the larger panels.

**Fix.**
- The server computes the size for the selected display. Over the limit, it drops sub-items from the end and reports it in `/api/status` and the editor.
- The firmware reads one extra byte to tell "exactly full" from "too big".

## 11. An alert wakes a panel that was put to sleep by hand, and it stays awake afterwards — Low

**Where.** `components/epf/epf_core.h:596-605`, `:632-646`.

**Repro** (`scen.cpp (b)`). Manual sleep, then an alert arrives and ends: the
panel is awake (`sleeping=0`) and starts rotating all day.

**Fix.** Remember `sleeping_` and `sleep_manual_` when an alert takes over,
and restore them when it ends.

## 12. A refresh request that arrives during a download is dropped — Low

**What.** `refetch` is `mode: single`, and `EpfClient::start_fetch` returns
false while a download runs. The YAML only logs "A download is already
running". If the timed download started just before the add-on rendered new
content, the push that follows is lost, and the change (or an alert) waits one
interval.

**Where.** `addon/app/firmware/panel.yaml:344-356`, `epf_client.h:43`.

**Likelihood.** Low. The delay is at most a minute at this panel's interval,
but up to an hour at longer intervals.

**Fix.** When a fetch is refused as busy, set `pending_refetch` and start it
after `poll()` reports the running one finished.

## 13. A huge page step freezes the panel until the watchdog resets it — Low

**What.** `step_category_` loops once per step: `page_step(2000000000)` from a
Home Assistant automation, or `POST /api/action/page {"delta": 2000000000}`
with the token, spins the main loop.

**Where.** `components/epf/epf_core.h:403-405`, `:705-712`; the server passes
any integer at `web.py:549`.

**Repro** (`scen.cpp (c)`). 200 million steps take 0.29 s on this Mac, so many
seconds on an ESP32-S3, which is past the task watchdog.

**Fix.** Reduce `delta` modulo the number of categories before looping, and
clamp it on the server.

## 14. Firmware: overlay geometry isn't bounds-checked — Low

**What.** The parser accepts any pill coordinates. `draw_overlays` then loops
over the full given rectangle.

**Repro.** The fuzzer (60,000 mutated files, CRC re-fixed, AddressSanitizer
and UndefinedBehaviorSanitizer) found **no memory errors**, which is good. But
`pill_y1=65535, sub_x1=65534` made one overlay take **25.7 s** on the host.

**Where.** `components/epf/epf_core.h:187-202`, `:255-259`.

**Likelihood.** Very low. It needs a forged server (frames travel as plain
HTTP on the LAN, so someone on your network could do it) or a server bug.

**Fix.** In `parse_stream`, clamp or reject `pill_*`, `cat_x0`, `sub_x*`
outside the logical width and height, and cap `pill_width`.

## 15. One bad element field stops all rendering — Low

**What.** `build_frames` reads `int(el.get("hours", 24))` outside
`render_page`'s per-element guard. `sanitize_layouts` doesn't check element
fields.

**Where.** `addon/app/frames.py:350-353`, `layouts_store.py:86-94`. The same
pattern is in `api_preview` (`web.py:478-480`).

**Repro.** Save a curve element with `"hours": null`. It saves fine, then
every render fails with `TypeError` and the panel freezes on its last frames.
The new editor deletes empty number fields, but `Infinity` serialises as
`null`, and the classic editor and hand edits can produce it.

**Fix.** Parse every element number through one tolerant helper (as
`layout._clamp_box` does), and guard each page's build so one page can't stop
the others.

## 16. Smaller things

- **Non-ASCII token returns 500 on the LAN port.** `hmac.compare_digest` raises for non-ASCII strings: `GET /frames.epf?token=%C3%A9` gives 500 and a traceback in the log (`frame_token.py:52`). Compare bytes instead.
- **Widget gates log `AttributeError` at every start.** `compute_*_active_window` returns `None` before the first fetch, and `_evaluate_widget_gate` calls `.get` on it (`frames.py:203-209`). The page is correctly hidden, but the log is noisy. Seen in today's log.
- **The rotation reshapes almost every minute.** The live log shows "pages changed, pushing" on most renders, because the flight page's sub-item count (1, 2 or 3 aircraft) and identities change. Linger keeps the page but not its size. Each push is an extra download and redraw, and it feeds the ghost-clearing count. Consider a fixed slot count for flights, or not pushing for sub-item-only changes.
- **Duplicate rotation entries share item identities.** A page listed twice gets distinct category ids but identical sub-item ids, so `find_page_` always finds the first copy, and a lock on the second copy jumps to the first after a reload (`subitems.py:164-174`).
- **`show_page` while asleep only wakes.** Home Assistant's `show_page` or `page_step` while asleep wakes the panel without going to the page. All Home Assistant actions also count as "a person", which blocks full refreshes and auto-rotation for 15 s (`epf_core.h:381-384`). Check that this is intended.
- **The 0.8 migration can be marked done without running.** `_migrate_once` marks `dedupe_v1` done even when the registry couldn't be read, because the loop has nothing to do (`mqtt_bridge.py:284-323`). Harmless here (already migrated), wrong for a fresh upgrade that starts while Home Assistant is down.
- **Small caches that never shrink.** `runtime.PUBLISHED`, `runtime.FEED_ITEMS` and `sources/flights._aircraft_cache` are never pruned. They're bounded by your own configuration plus editor use, and the add-on uses 65 MB today. Not a real leak.
- **Checked and found sound.**
  - The Ingress-only check (uses the socket peer, handles `::ffff:` IPv4-mapped addresses, ignores forwarded headers).
  - The static route and font allow-list.
  - The new editor's `innerHTML` use (icons only), and the classic editor's paths, which all go through `esc()`.
  - The token switch-over logic.
  - Atomic file writes.
  - The front/back buffer handoff between the download task and the main loop (acquire/release on `state_`, the swap only in `poll()`).

## Risky areas that need tests

1. **Secret hygiene:** run each failure path with a fake token and assert it never appears in captured stdout or API responses (finding 1).
2. **Render isolation:** a slow or hanging source, and a slow Home Assistant, must not delay `refresh_frames` past a bound (findings 2, 4).
3. **Concurrent `refresh_frames`:** the last saved layout always wins (finding 5).
4. **MQTT lifecycle:** a failing-but-configured source is never withdrawn, and a removed one is (finding 3).
5. **Home Assistant outage:** values and alerts are stable across a 502 window (finding 4).
6. **Firmware resting state:** a failed download while asleep or quiet is retried, manual sleep survives an alert, and a busy fetch is queued, not dropped (findings 6, 11, 12).
7. **Parser hardening:** keep the fuzzer as a test (bounded iterations), and add geometry bounds (finding 14).
8. **Frame size per display model** against `BUFFER_CAPACITY` (finding 10).
9. **`sanitize_layouts` with hostile element fields** (null, strings, `Infinity`, nesting) followed by a full `build_frames` (finding 15).
10. **Source rename** keeps the secret (finding 8).
